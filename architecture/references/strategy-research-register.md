# Strategy foundation research register

**Retrieved:** 2026-10-09. This register records source-backed findings used by
the proposed strategy and architecture. Official product documentation
establishes documented features and constraints; the live GitHub observations
remain separately recorded in `system-evidence.yml`. Public project documents
are examples of author practice, not standards or proof of outcomes.

| Area and source | Claim supported | Limit | Local architectural implication |
| --- | --- | --- | --- |
| Strategy concepts — [Brosch (2023), corporate purpose construct review](https://link.springer.com/article/10.1007/s11573-023-01137-9), journal article | Research does not use universally agreed definitions for purpose, mission, and vision; the review proposes distinguishing why an organization exists, what it does now, and a desired future. | A literature review cannot determine this organization's wording or validate its market. | Keep the three statements separate, define them locally, and leave them proposed for maintainer review. |
| Mission statements — [Braun et al. (2012), review](https://doi.org/10.5172/jmo.2012.18.4.430) and [Desmidt et al. (2011), meta-analysis](https://doi.org/10.1108/00251741111120806), peer-reviewed research | Mission development and implementation conditions matter; the meta-analysis reports a small positive relation with financial-performance measures and sensitivity to operationalization. | Association is not proof of causation or of software-factory outcomes. | Measure strategic outcomes against dated baselines; mission wording alone is not an evaluation. |
| Strategy implementation — [Sull, Homkes, and Sull (2021), review](https://doi.org/10.1016/j.emj.2020.09.005), European Management Journal | The systematic review treats implementation as a multi-part, dynamic process involving managerial action and enabling conditions; it notes that strategy implementation is often treated as a black box. | A cross-sector review does not validate a particular operating model for this lab. | Make the translation from strategy to goals, prioritized Issues, delivery changes, measures, and review evidence explicit so execution stays inspectable. |
| Software goal alignment — [Basili et al., GQM+Strategies (2014)](https://arxiv.org/abs/1402.0292), author preprint | The method links organizational strategy to operational software goals and measurement goals. | It proposes and illustrates a method; it does not show measured impact for this organization. | Use explicit many-to-many goal/measure traceability and treat the graph as evidence structure, not as a mandatory waterfall. |
| Measure selection — [Kershaw and Malhotra (2012), empirical study](https://doi.org/10.1504/IJAAPE.2012.043964), publisher abstract | Their study reports that strategy-aligned measures may focus managerial effort, while a highly responsive secondary measure can divert effort from primary goals. | The result is context-specific and does not directly measure agentic delivery behavior. | Treat metric gaming and local optimization as risks; report baselines, denominators, uncertainty, and complementary user, quality, security, and delivery measures. |
| Architecture description — [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html), international standard, second edition published 2022-11 | The standard addresses architecture description for systems and enterprises and supplies stakeholder/concern/viewpoint/view concepts. | The public catalogue page exposes metadata, not the full normative text; this repository does not claim conformance. | Use the terms to organize stakeholder concerns and views, while retaining arc42 as the practical documentation structure. |
| Architecture documentation and quality — [arc42 Section 1](https://docs.arc42.org/section-1/) and [Section 10](https://docs.arc42.org/section-10/), living framework documentation | arc42 separates context/goals from quality requirements; a quality scenario names source, stimulus, environment, artifact, response, and response measure, and may describe use, change, or failure. | arc42 is a template and guidance, not evidence that a system meets a quality goal. | Keep priorities short in §1, define observable response measures in §10, and distinguish target scenarios from tests that ran. |
| Domain boundaries — [Eric Evans, Domain-Driven Design Reference (2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), author-published pattern summary | A bounded context defines where a model applies; a team develops a ubiquitous language within that explicit boundary, and a context map describes relationships between contexts. | A pattern reference does not determine this organization's domain boundaries or prescribe repository boundaries. | Keep the four existing domain contexts and their language; treat Architecture Authority and GitHub adapters as owners/surfaces, not new contexts without distinct models, invariants, and lifecycle. |
| Decision records — [MADR README and templates at commit `ba75bb1`](https://github.com/adr/madr/tree/ba75bb1b20d42af5746b246ad348c202419ae681), open-source project documentation; inspected `develop` | MADR offers explained, minimal, bare, and bare-minimal Markdown templates, with linting and release/version practices. | The repository documents one useful format; it is not a universal ADR standard and the latest development branch may change. | Preserve the local Architecture-owned ADR family and its validator; use templates only where compatible with existing IDs, ownership, and release contracts. |
| GitHub portfolio — [Projects overview](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects), [Project API](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), and [organization Issue Fields](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-issue-fields), product documentation | Projects support issue, pull-request, and draft items; table, board, roadmap, charts, custom fields, and API automation. Organization Issue Fields are issue-owned and shared across Projects; editing their values from a Project syncs back to the Issue. Project custom fields are scoped to one Project. Organization-only Issue Fields do not appear in public or internal Projects. | Docs describe supported features, not this organization's selected Project or effective field visibility. The live inventory is complete for the queried owners and shows Projects capability flags and no Project nodes. See `system-evidence.yml#project-inventory-20261009-1153`. | Use an organization Project as a proposed planning surface, preserve Issue-owned lifecycle/priority semantics, avoid duplicate concepts in custom fields, and keep Project planning distinct from source-Issue authorization. |
| GitHub work types — [Organization Issue Types documentation](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-types-in-an-organization) and [REST Issue Types API](https://docs.github.com/en/rest/orgs/issue-types), product/API documentation | Native organization Issue Types can classify work and appear in Project views; the API has an organization-scoped listing operation with explicit token permission requirements. | API access and UI access have separate actor/resource permission boundaries; an Issue Type does not itself authorize execution. | Preserve the nine observed native types and keep routing/readiness gates in the owning Issue and Control Plane. |
| Markdown renderer — [GitHub Flavored Markdown specification](https://github.github.com/gfm/), specification 0.29 (2019) | GFM defines GitHub's CommonMark-based Markdown extensions and rendering behavior. | It is GitHub's dialect, not a universal interchange standard; GitHub also sanitizes rendered HTML. | Use portable headings, links, tables, and fenced code in canonical docs; do not assume every host renders GitHub extensions identically. |
| Project-specific strategy examples — [hyper Vision](https://github.com/hyperium/hyper/blob/f1b0876495cb042d228e8db00740056152ac131c/docs/VISION.md), [mdflow Vision](https://github.com/johnlindquist/mdflow/blob/e3777512bf92d7ab82b6e515430c3b1cfb0cc286/VISION.md), and [AIDD `vision.md`](https://github.com/paralleldrive/aidd/blob/9a7c8e363020632ac0f21e75ac3be6175789288e/vision.md), repository files pinned to commits inspected 2026-10-09 | Examples combine a durable direction with audience/use cases, tenets or principles, boundaries/non-goals, and evaluation-oriented expectations. | These files express their authors' intentions; they do not establish a common Markdown standard, adoption, quality, or independently measured impact. | Keep one canonical editable organizational strategy; make goals, ownership, measures, non-goals, decisions, and evidence explicit, then link to it from context-specific instructions. |
| Agent checks and human decisions — [OpenAI Agents SDK guardrails and approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals), vendor documentation | The guide distinguishes automatic guardrails from human review and describes pausing for approval before sensitive tool actions. | Guidance about an SDK workflow does not prove the local Control Plane enforces equivalent checks. | Retain deterministic authorization and explicit human merge/release boundaries; do not treat model judgment as permission. |
| Evaluation tooling lifecycle — [OpenAI API deprecations](https://developers.openai.com/api/docs/deprecations), vendor lifecycle notice inspected 2026-10-09 | OpenAI announced Evals platform deprecation on 2026-06-03; existing evals are scheduled to become read-only 2026-10-31 and the dashboard/API are scheduled to shut down 2026-11-30. Agent Builder is also scheduled to shut down 2026-11-30; the notice says ChatKit remains available. | These are announced schedules and may change; they do not mean this repository currently uses either product. | Keep the local evaluation case/result contract and deterministic replay provider-neutral. Recheck provider lifecycle before any integration and make no local evaluator depend on the retiring dashboard/API. |

## Reading this evidence

The proposed one-Project/two-view portfolio topology is a local decision option,
not a GitHub recommendation or applied setting. Current organization API
capability flags and the full empty Project inventory are recorded in
[`system-evidence.yml`](system-evidence.yml). The authenticated user has an
active organization admin role, but GitHub App access remains unverified and
the Project topology remains a human decision in Architecture
[#15](https://github.com/agentic-delivery-lab/agentic-delivery-architecture/issues/15);
the role and OAuth scopes do not satisfy that separate change-approval gate.
